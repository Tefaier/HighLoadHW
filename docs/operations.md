## 1.2 Стратегия деплоя

Деплой в виде комбинации canary и rolling. 
- canary имеет плюс, что можно проверить корректность релиза до того, как он становится доступен всем. Единственное минус, что это поставит требование иметь несколько реплик даже на api сервис, где большой rps не ожидается. Также изоляция не будет полной, потому что новые и старые инстансы будут общаться через бд и брокер сообщений. Тем не менее это позволит по мониторингу понять, если с релизом что-то не так, и купировать потери до выкатки на большее количество реплик.
- rolling не избежен при большом количестве инстансов. Order service будет иметь множество инстансов как в canary, так и обычной части. Чтобы rps живые реплики выдерживали rps нужно будет rolling делать, по 10% инстансов за раз (минимум 1).

Накатывание новой версии конкретного инстанса.
- liveness. Сервисы будут отвечать alive, когда запустился fastapi (способен ответить на ручку). ready будут отвечать когда установилось соединение с бд и очередью (в случае если сервис использует), чтобы гарантировать возможность обрабатывать запросы.
- Для сервиса, чтобы не потерять заказы, важно обеспечивать корректную остановку инстансов. При получении сигнала он останавливает запуск новых cron таск и переводит ready статус в 503. Потом через 3 минут приложение убивается.

Накатывание новой версии схемы бд.
- для всех случаев expand/contract метод обновление. Исключение, если добавляется например новая таблица или то, что не использовалось - тогда expant/contract не нужен.
- для простых действий с метадатой таблиц обновление через обычные скрипты. Если обновление по времени растер пропорционально размеру таблицы, то по возможности через `pg_migrate` или через механизмы postgresql, которые позволяют избежать блокировки (например `create index concurrently` или `not valid`). Нужно будет учитывать необходимое место для работы `pg_migrate` на создание дубликата таблицы, если будет использоваться он.

### Логи

Json формат логов. Запись в stdout, откуда уже отправляются в хранилище (loki). Проще в реализации.

Обязательный поля:
- time (YYYY-MM-DDTHH:mm:ss.sssZ) (все в UTC+0)
- service_name
- host (service, сервер, номер)
- rid
- message
- level

Необязательные поля:
- trace_id (по возможности всегда)
- meta (все остальное в формате объекта json)

Для nginx:
- host
- upstream
- rid
- status
- request

Для библиотек логи ограничены: только логи запросов и ошибок к бд, rabbitmq. Отдельно nginx где логируем на моменте ответа клиенту или завершения соединения (когда клиент оборвал соединение). Дополнительно логируем все внешние запросы (uri, time, error). Логируем начало, окончание, ошибки cron задач. Логируем запись и чтение из очереди (только (не) успех)

Body запросов не логируем, потому что они могут быть бесконтрольно большими. Headers запросов не логируем, потому что там часто передаются чуствительные данные и их впринципе может быть много.

Если лог принадлежит ошибке, то она с `stacktrace` идет в `message` в конце.

# 2 Доступность

## 2.1 Целевая доступность системы

Для критичного пользовательского пути “поиск → корзина → оформление заказа → оплата → статус заказа” целесообразно зафиксировать доступность на уровне 99.95%.

Для менее критичных контуров можно держать более мягкие SLO:
- пуш/SMS-уведомления — 99.9%;
- кабинет ресторана и административные функции — 99.9%

### Обоснование:
99.9% для нашего сервиса с заказами и оплатой - это заметный риск для бизнеса (0.001 * 365 * 24 = 8.76 ч простоя). Скорее всего, этот простой будет не ночью, что в сумме даст большую потерю клиентов и заказов (люди не будут ждать, пока приложение встанет на ноги, они пойдут к конкурентам)
99.95% это в два раза меньше простоя.

Для остальных сервисов операции происходят не так часто или не так важны (уведомления могут прийти и попозже; администраторы вряд ли сидят в сервисе 24/7)

### Потери в цифрах

Пусть:
Потери от простоя = среднее число заказов в минуту * средний чек * длительность простоя

у нас:
- 2* 10^6 заказов/день -> в минуту 1.39 * 10^3 заказов (см [requirements.md](./requirements.md#L119))
- Для среднего чека оценим снизу в 1000 рублей

Итого даже 15 минут простоя в пиковой время дадут >250к рублей потерь; так что вложение в архитектуру рентабельно

### Ожидания юзеров

Очевидно, основная часть заказов будет приходится на пиковые часы, и у людей не будет времени ждать ответа от нашего сервиса.

## 2.2 RPO и RTO для критичных компонентов

| Компонент | Роль | RPO | RTO | комментарий |
| :--- | :--- | :--- | :--- | :--- |
| БД заказов | ground truth | ~5 сек |  <15 мин | Потеря заказов почти недопустима |
| Очередь | Асинхронная доставка, уведомления | 30 сек - 1 мин |  15-30 мин | - |
| Кэш | ускорение операций, временные данные | не критичен |  5-15 мин | Кэш можно просто пересоздать при восстановлении сервиса |

Пояснения:
- Если очередь упала, можно временно переключиться на синхронную обработку, пока очередь не поднимется (поэтому очередь может в теории подниматься дольше чем бд заказов)

## 2.3 Стратегия резервирования

1. БД - active/standby. standby сервер получает данные асинхронно

    #### Альтернатива (active/active)
      - Плюсы: 
        - Если один регион упал — второй уже работает
        - Нагрузка делится между узлами
        - переключение в случае отказа очень быстрое
      - Минусы: 
        - проблемы с логической консистентностью (Пользователь оформил заказ в регионе А, курьер принял его в регионе Б, а потом одновременно пришла отмена)
        - сложность содержания
        - цена содержания
    
    #### Итог:
    
    Поскольку изначально обозначили ограниченный бюджет (см. [requirements](./requirements.md#L209)), active/standby выглядит более привлекательно, пусть и:
    1) потеряем время на переключение в случае остановки первого сервера
    2) возможно последние секунды транзакций не сохранятся (из-за асинхронного Data recovery) 

    Также стоит учитывать, что проблемы с консистентностью могут произойти в критически важной оплате или заказах, что повлечет проблемы для бизнеса


2. Очередь - active/standby. standby очередь получает данные асинхронно

    #### Альтернатива (active/active)
      - Плюсы: 
        такие же, как и у active/active базы данных
      - Минусы: 
        - цена содержания
        - сложность содержания
    
    #### Итог:
    
    Ограниченный бюджет, небольшая команда, только стартующий сервис. Логичнее всего начать с active/standby решения

3. кэш - (active/active).
      - Плюсы: 
        такие же, как и у active/active базы данных
      - Минусы: 
        - цена
        - при падении первого узла, будет деградация второго засчет нагрузки
    
    #### Итог:
    
    вариант active/active кажется предпочтительнее, чем active/standby. Данные внутри кэша не важны, если часть из них потеряется при перераспределении нагрузки на второй нод, то ничего страшного; зачем платить за standby кэш, когда он может служить для ускорения системы?



## 2.4 Maintenance window

Для пользовательского API и критичного пути оформления заказа плановое окно недоступности не предусмотрено.
Система проектируется под zero-downtime deployment с использованием (см. [deployment](#1-deployment)):

- canary deployment;
- rolling update;
- readiness/liveness probes;
- graceful shutdown;
- expand/contract migrations

Большинство изменений должно выполняться без остановки обработки заказов

### Допустимые maintenance windows

Для редких инфраструктурных операций допускается ограниченное maintenance window:

- не чаще 1 раза в месяц;
- в период минимальной нагрузки (т.е. например ночью);
- длительностью до 30–60 минут;
- с предварительным уведомлением
