
# Адаптация k6 под 2 vCPU / 8 GB

Смысл настройки здесь такой: не задавать “магический” максимальный RPS, а доводить систему до рабочей насыщенности и смотреть на метрики хоста.

## Что изменить

### 1. `k6/load.js`
Это тест под **длительную целевую нагрузку**.

Сейчас дефолт:
- warmup: `200 RPS`
- steady: `800 RPS`
- длительность steady: `15m`

Это безопасная стартовая точка для 2 vCPU / 8 GB.  
Дальше повышайте `TARGET_RPS`, пока на хосте не будет:

- CPU контейнера/процесса в диапазоне **70–90%**
- RAM заметно занята, но без OOM / swap thrashing
- disk I/O не упирается в 100% util
- p99 остаётся в рамках требований

Пример:
```bash
TARGET_RPS=1000 ./run.sh load
TARGET_RPS=1200 ./run.sh load
TARGET_RPS=1400 ./run.sh load
```

### 2. `k6/stress.js`
Это **максимизирующий** сценарий.  
Я изменил его так, чтобы он шёл ступенями:

- 300 → 500 → 700 → 900 → 1100 → 1300 → 1500 RPS

Это уже ближе к “разогреть 2 vCPU в пол” и увидеть точку деградации.

Если система ещё не насыщена, повышайте:
```bash
STAGE_6_RPS=1800 ./run.sh stress
```

Если начинает валиться слишком рано, снижайте:
```bash
STAGE_4_RPS=800 STAGE_5_RPS=900 STAGE_6_RPS=1000 ./run.sh stress
```

### 3. `run.sh`
Оставил экспорт HTML-дашборда как есть. Это правильно, его менять не нужно.

## Что обязательно мониторить дополнительно

k6 сам по себе не видит CPU/RAM/disk I/O хоста.  
Для оценки нужно параллельно снять системные метрики:

```bash
docker stats
pidstat -durh 1
vmstat 1
iostat -xz 1
```

Если сервисы в Docker, полезно смотреть именно контейнеры:
```bash
docker stats order-service api-service tracking-service
```

## Как интерпретировать результат под ваши критерии

Хороший результат:
- высокий RPS
- CPU держится в коридоре 70–90%
- RAM используется
- disk I/O тоже нагружен
- p99 и error rate не “ломаются” преждевременно

Плохой результат:
- 20 RPS и CPU уже 100% → код/инфраструктура неэффективны
- 300 RPS и CPU 20% → bottleneck не в CPU, ищите БД, connection pool, блокировки, сеть, threadpool

## Практический порядок прогонов

```bash
docker compose up --build -d
./run.sh smoke
TARGET_RPS=800 ./run.sh load
TARGET_RPS=1000 ./run.sh load
./run.sh stress
```

## Важный смысловой момент

Для **оценки** лучше фиксировать не один “максимальный RPS”, а **максимум при приемлемом p99**, и рядом писать:
- CPU контейнера
- RAM
- disk I/O
- error rate

Именно это показывает, что система нагружается эффективно, а не “задыхается от себя”.
